# 底盘实测清单与记录要求

本清单适用于 RoboMaster A 板的单板 X 型四全向轮底盘。代码基线为 `d5821ac`，常规日志标识为 `fw=20261111 frame=19 mode=2`。测试使用卡尔曼影子模式（SHADOW），候选补偿只记录，不加到轮速参考。

截至 2026 年 11 月 11 日，该基线已通过 32 项 Python 测试和默认 ARM 构建。新版 J-Link 链路、平移启停表现和轮速与 IMU 的高频时间对齐还需要现场数据。此前 `frame17` 的落地试验观察到右漂，已有日志不足以判定原因。

| 顺序 | 实测项目 | 要回答的问题 |
| --- | --- | --- |
| 1 | RTT 通道 0 双速率对照 | 哪档速率能稳定保存完整日志？ |
| 2 | 静止与低速平移启停 | 上电后观测是否正常，推杆和松杆时底盘实际怎么动？ |
| 3 | 四轮检查与落地原地旋转 | 右漂能否复现，轨迹与轮速或接地状态是否一致？ |
| 4 | WIMU 高频采集 | 四轮与 IMU 是否有足够的共同有效时间，可用于离线回放？ |

## 开测前

- [ ] 使用与其他执行机构隔离的底盘台架或底盘测试车，保留 IMU 和编码器采集链路。运动试验前清空区域，在静止状态下确认急停可以禁止底盘输出。
- [ ] 记录实际烧录产物、代码提交和产物 SHA-256。`frame=19` 是日志格式，修复前后的版本都使用该标识。若通过调试器加载 ELF，核对它与指定 HEX 来自同一构建。
- [ ] 记录载荷、地面、轮位（左前 LF、右前 RF、左后 LB、右后 RB）、IMU 安装和供电。首轮用普通固件。确认日志出现 `CONFIG`，`mode=2`，且 `CONFIG` 的 `direct=1`。等惯导初始化和采集稳定后再开始有效段。

## 1. 验证 RTT 通道 0

- [ ] 固定同一固件、J-Link、线缆、供电及采集入口。推荐 RTT Viewer 直连，仅用一个客户端保存通道 0 原始文本，两档均关闭 Live Watch。记录采集会话实际使用的 SWD 速率。
- [ ] 分别以 **100 kHz** 和 **1 MHz** 采集。每档至少两轮。每轮先采 **30–60 秒**稳定静止段，再在独立底盘上做同一组低速前后移动和松杆动作。断连或复位后新建文件。
- [ ] 保存整轮原始文本。需要排除启动段时，另存分析副本，注明起止时间或序号，并保留完整帧和 `CONFIG`。以下命令从工程根目录审计 `100k_static_01.txt`。

  ```powershell
  python -B tools/audit_chassis_text.py build/rtt-validation/100k_static_01.txt --output build/rtt-validation/100k_static_01.audit.json
  ```

| 通过项 | 判定方法 |
| --- | --- |
| 核心帧完整 | `missing_core_frames`、`incomplete_frames`、`sequence_unchecked_transitions` 均为 0。根据 `CONFIG` 的 `period_us` 和 `decimation` 核对核心帧频率，默认约 10 Hz。 |
| 计数器稳定 | 取有效段首尾完整 `STATUS`，`qdrop`、`tdrop` 的增量均为 0。 |
| 低频诊断持续收到 | `CONFIG`、`DETAIL`、`HEALTH` 在稳定段持续出现，约每秒一次。 |

静止和运动的重复采集都通过后，选用实测稳定的速率继续后续试验。若 `qdrop` 增长，先查快照队列。若 `tdrop` 增长，先查 RTT 写出及主机连续读取。计数都不增长但出现缺帧时，检查保存、断连和分段。历史日志只能提供排查方向，两档新版数据都要留存。

## 2. 验证静止、平移和停车

- [ ] 静止时检查四轮反馈、IMU 样本年龄与序号、`HEALTH` 计数以及估计速度。`accepted_seq` 应持续前进，普通轮询时 `not_ready` 可以增加。若出现持续假速度、传输错误或样本停滞，保留该段并先复查，再做运动测试。
- [ ] 在平整地面低速验证前后和左右方向。每个轴至少重复两次「起步 → 短时匀速 → 松杆」，再做低速反向，记录固定机位视频或地面刻度上的轨迹。视频和日志标记同一动作，便于对照。
- [ ] 比较 `KF` 的平移输入和参考、`WHEEL` 的目标与反馈、`STATUS.output_enabled` 和实际运动。重点记录方向、起步迟滞、松杆后停车距离、余速和侧偏。影子模式下核对 `cmd_g_mmps` 与 `ref_g_mmps` 一致。

通过时应看到运动方向与输入一致，低速启停可重复，松杆后平移参考回零且车辆可控停车，无持续余速、异常侧偏或意外输出。约 10 Hz 的文本用于判断趋势。需要量化从推杆到实际运动的延迟时，用高频控制记录并同步标记输入和实际运动。

## 3. 复核落地右漂

- [ ] 先检查四轮滚子接地、松动或偏心、传动阻力与安装方向。逐轮记录相同载荷下的有效滚动直径和测量方法。将实测值与 `CONFIG` 记录的轮径分开列出。
- [ ] 确认平移启停通过后，在同一地面和载荷下做低速顺、逆时针原地旋转，平移输入保持回中。标记底盘中心和初始朝向，用地面网格或固定机位拍摄。每个方向至少两轮，记录实际转速、稳态区间、中心净位移的方向与距离。
- [ ] 对照同一段的四轮目标与实际轮速、轮位样本年龄、轮速缩放和 `OBS` 状态。将外部中心轨迹作为漂移证据。轮速反解位移用于对照。

先报告漂移是否在相同条件下复现，以及是否随旋转方向或轮速误差重复变化。历史记录给出的暂定验收目标是 **稳态 20 秒中心漂移不超过 1 cm，重复两次**。只有外部测量能分辨 1 cm 且稳态段达到规定时长，才据此判定。数据不足时报告测得的位移与分辨率。

## 4. 验证 WIMU 高频采集

- [ ] 通道 0 验收通过后，用同一代码基线的独立 `WHEEL_IMU_CAPTURE=1` 构建。重新记录固件指纹，保存通道 1 原始 `.wimu` 及同期通道 0 文本。先采静止，再采直线启停和匀速。前述旋转试验通过后，可补采低速原地旋转。每种工况至少采三份，留一份作独立复核。
- [ ] 用仓库的 `tools/decode_wheel_imu_capture.py` 解码。核对长度、CRC、结束原因、各数据流记录数与时间戳。记录提前冻结、溢出、时钟代际变化及数据断点。
- [ ] 对每份采集标注 IMU、四轮、朝向和控制流的共同有效区间。用于完整回放的片段应在同一时钟代际内连续覆盖至少 **0.25 秒**。单次抓取最长 **350 ms**，因此需要核对实际重叠时长。台架缺少朝向反馈时，标注完整回放仍待补测。

通过时应能完整解码二进制，各必需数据流有连续共同窗口，启停或稳态事件在高频记录中可定位，且同期通道 0 仍满足第 1 项。通过后再进入离线对齐、去重力和观测残差比较。

## 回传材料

每轮交付原始日志、对应的审计或解码 JSON、现场记录和可用的视频。可用 `100k_static_01.txt`、`1mhz_motion_02.txt`、`wimu_startstop_01.wimu` 这样的文件名，方便匹配速率、工况和轮次。

| 记录项 | 填写内容 |
| --- | --- |
| 版本与设备 | 提交号、固件文件及 SHA-256、日志 `fw/frame/mode`、采集入口、实际 SWD 速率 |
| 工况 | 轮次、载荷、地面、动作和方向、有效起止时间或序号、任何断连或复位 |
| 结果 | 缺帧数和计数增量、停车或漂移测量、WIMU 共同有效时长、通过或未通过及依据 |
| 文件 | 原始文本或 `.wimu`、审计或解码 JSON、视频文件名及对应时间点 |

首轮至少回传 **两档 RTT 各两轮**的原始日志、审计结果和采集配置。后续运动和高频数据沿用同一记录口径。
