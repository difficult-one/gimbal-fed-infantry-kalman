## 1. 先确定要实现什么

### 1.1 推荐目标

正常驾驶实现以下链路：

```text
键鼠/遥控器目标速度（云台系或底盘系，必须明确）
    -> 坐标变换、速度上限、加减速规划
    -> 底盘速度误差 PI + 可选动力学前馈
    -> 目标 Fx/Fy/Mz
    -> 四轮力矩分配
    -> 标定后的轮端力到电流换算
    -> 电流/功率/温度/故障约束
    -> C620 内部电流环
    -> 电机编码器 + 底盘 IMU 反馈到速度外环
```

这仍然是力矩执行的底盘，不是必须退回原来的四轮速度 PID。外环负责决定当前需要多大的力，内层负责执行力矩。没有软件 D 项的 PI 也属于闭环控制，不必为了叫作 PID 而增加微分噪声。

建议保留三个清晰分离的模式：

| 模式 | 输入 | 用途 |
| --- | --- | --- |
| 传统轮速模式 | 旧工程速度量 | 基线、回退，不改旧单位 |
| 运动闭环力矩模式（新增） | m/s、m/s、rad/s | 正常比赛驾驶的主线 |
| 直接力矩模式（已有） | N、N、N·m | 标定、受限推力实验，不直接作为常规驾驶 |

传感器力跟踪、估算力反馈修正和导纳模式在主驾驶稳定之后独立验证。不要同时叠加所有环路再一起调参。

### 1.2 必须纠正的认识

- 当前估算模式没有软件力 PID，但 C620 内部仍有电流闭环，速度阻尼也使用了反馈。
- 可以用电机实测电流做估算力闭环，不是一定需要新增力传感器。但是它闭环的是模型估算的电机驱动力，不是独立测量到的地面接触力。
- 真实接触力闭环需要测到所关心的力，或者建立并验证可靠的观测器；传感器的安装位置决定它究竟测到了什么，并非随便装一个测力计就能代表四轮接地力。
- “力跟随目标”不能替代“速度跟随目标”。四轮等力也不意味着四轮等速。
- 松键停车、故障撤力、断电是三种不同动作：正常松键可以主动制动；反馈失效时不能依赖无效测量继续制动；撤掉电流不保证惯性运动立刻停止。
- 不保证力矩架构必然优于调好的速度架构。必须用相同场地、功率、轮胎、负载做 A/B 测试，达到或超过旧速度模式才考虑比赛使用。

### 2.2 以前的数据解释了什么

用户最近提供的日志标记为 `v20261008`，不是最新源码的 `v20261008B`。其中：

- 按 W：`target=-10000,0,0`，即当前模型输入 `Fx=-100 N`。
- 启动时四轮 `ref` 约为 `1840,-1845,1841,-1847 raw`。
- 启速退出后 `ref` 约为 `330,-330,330,-330 raw`，四轮转速约为 1000~2500 deg/s。
- 松键时曾出现 `ref=-26,19,-26,26`，轮速仍约为 `1348,-976,1312,-1339 deg/s`，原阻尼制动很弱。
- 源码已增加 `0.60 raw/(deg/s)` 的松键制动，但还不能用旧日志证明这一版的实车效果。

编码器转速是电机转子速度，不是输出轮速度。按下述旧日志采集时配置半径0.06 m、减速比19（frame16已将实车半径修正为0.0725 m，下述旧数值保留历史含义）：

```text
轮缘速度 = speed_aps * (pi/180) / 19 * 0.06
1500 deg/s -> 约 0.083 m/s 轮缘速度
纯 X 平动且四轮符合几何关系 -> 约 0.117 m/s 底盘速度
```

所以“转速数字上千但车很慢”并不矛盾。当前目标量也不是目标速度，提高固定力不等于设定更高且可控的行驶速度。

旧数据没有独立测力标定和可靠的底盘速度测量，不能据此算出正确 Kt，也不能仅凭低频打印断言电流瞬态正常。四轮速度不同不能仅归因于 RF 电机故障。

## 3. 前置条件：先准备，再写主控制器

### 3.1 必备设备

- 可快速操作的硬件断电/急停装置；旁边有操作员，首次测试禁用发射机构。
- 能可靠架空底盘的支架，轮胎与电线、衣物、工具保持距离。
- 空旷平地、比赛相近地面材料、标记距离和停车区；有防碰撞空间。
- 稳定供电，检查电池、电源线、接插件、电容的额定电流与温度。
- 下载器与日志采集工具，能够记录固件版本、时间戳和参数。
- 卷尺/卡尺、电子秤，用于测轴距、轮距、负载下轮半径、整车质量。
- 固定的力臂、拉力计/测力传感器、可靠夹具，用于输出轴转矩标定；没有这些也能先调受限 P 外环，但不能声称力值准确。
- 独立速度对照手段：短距离视频测时、光电测速、外部定位或光流等至少一种。严肃评估打滑时必须有轮速之外的参考。
- 母线电压/功率测量来源及采样说明。普通母线电流表不能直接标定电机相电流。

### 3.2 机械条件

1. 逐轮检查轴承、减速箱、轮胎、全向滚子；左右阻力差异先修机械，不用软件长期掩盖。
2. 实测并记录 `WHEEL_BASE`、`TRACK_WIDTH`、`RADIUS_WHEEL`。源码现值为350 mm、300 mm、72.5 mm；半径按用户确认的145 mm外径修正，轴距/轮距及负载下有效滚动半径仍需核验。共享轮径变更影响力到转子力矩及反馈速度换算，力控效果需重新验证。
3. 实际减速比核对型号，当前宏是 19。
4. 确认四轮均匀接地、无悬空、轮子驱动方向与模型一致。
5. 实测完整比赛配置质量，弹丸、电池、云台和装甲等都算入。负载变化应进入测试矩阵。

### 3.3 IMU 条件，尤其重要

当前 `GimbalInit()` 和 `ChassisInit()` 都调用 `INS_Init(&g_imu_config)`。`modules/imu/ins.c` 的初始化是单例，两次调用会返回同一套 IMU 数据，不会生成两个独立传感器。

因此必须实测：

1. 固定底盘，只转云台。候选“底盘 IMU”的 yaw 角速度应接近零。
2. 固定云台相对底盘位置，手动转底盘。候选 IMU 应跟随底盘转动。
3. 确认 IMU 固定牢靠，安装轴与底盘坐标系一致；倾斜安装要做旋转变换，不能只改一个符号。
4. 冷启动静止校零，热机后检查零漂。为采样增加时间戳/序号，不能只检查 `isfinite()`。

如果板装在云台上，则它测的是云台姿态，不能直接用于底盘旋转反馈。选择：独立底盘 IMU；或先用编码器估计底盘角速度进行受限低速测试。用云台陀螺仪减去云台相对底盘转速也需要可靠的相对反馈、坐标变换和同步，不能未经验证直接上场。

当前 MPU6500 对外 `attitude_t.Gyro[]` 为 deg/s，动力学控制使用 rad/s，需要乘一次 `pi/180`。不要按其他 IMU 工程习惯重复换算。`GYRO2GIMBAL_DIR_YAW` 是云台相关符号，不应不加核对地当成底盘符号。

### 3.4 软件与安全条件

- 建立可回退的源码版本、参数表和已验证的传统速度固件；不要覆盖用户现有改动。
- 核对 CAN1 映射：LF=1、RF=4、LB=2、RB=3；注意数组顺序和 CAN ID 顺序不同。
- 四轮反馈新鲜度、遥控/图传新鲜度、任务超时均有实际时间判定。
- 命令发布者持续发布旧按键状态也可能绕过底盘话题超时，因此必须检查输入源自身在线和帧龄。
- 故障后必须重新解锁且先回中/松键，不能反馈一恢复就恢复上一条非零命令。
- 堵转检测用“较大电流 + 低轮速 + 持续时间”，阈值按实测正常启速时间和器件允许工况确定。不可无限周期性重试 1500 raw 脉冲。
- 过温、过压、欠压、CAN 故障有具体动作，阈值依据厂家说明和比赛配置，不照搬本文举例。
- 控制任务不阻塞打印；日志缓冲满时丢日志并计数，不延迟控制。

不满足以上条件时，只做架空或低速受限实验，不进入比赛主模式。

## 4. 单位、坐标系和符号只允许有一套定义

### 4.1 新模式全部使用 SI 单位

| 量 | 单位 | 转换位置 |
| --- | --- | --- |
| `measure.speed_aps` | 电机转子 deg/s | 反馈入口转换 |
| 输出轮角速度 | rad/s | 转子速度乘 pi/180、除减速比 |
| 底盘 `vx/vy` | m/s | 新模式命令和估计 |
| 底盘 `wz` | rad/s | IMU 转换一次或轮速反解 |
| 轮半径、力臂 | m | 毫米宏乘 0.001 |
| 合力/轮端驱动力 | N | 动力学和分配层 |
| 合力矩 | N·m | 动力学和分配层 |
| 电流 | A 或明确标记的 raw | 换算边界，不混用 |
| `dt` | s | 实际控制间隔 |

旧速度模式的 `VIDEO_CHASSIS_SPEED_SCALE=3000` 和 `wz=4000` 是旧链路的参考量，不能直接解释成新模式的 mm/s 或 deg/s。目前 `LimitChassisOutput()` 直接把 `vt_*` 写到以转子 deg/s 为反馈的 PID，不能把它当成已完成物理单位换算。

### 4.2 统一轮序与实测符号

统一顺序 `[LF, RF, LB, RB]`。

定义物理正方向、正旋转后，逐轮给小幅正/负电流，记录实际转动、编码器速度和电流符号。建立一张签名表。若物理轮驱动方向与反馈正向相反，统一通过 `sign[i]` 变换：

```text
物理轮速 = sign[i] * 原始轮速换算值
物理轮力 = sign[i] * 原始电流换算值
原始电流命令 = sign[i] * 物理轮力对应电流
```

下文参考核心要求 DJI 驱动的 `motor_reverse_flag`、`feedback_reverse_flag` 对这四个电机均为 NORMAL，符号由核心统一处理。如果继续使用驱动反向位，必须调整适配层，不能再乘一次同样的符号。

源码注释的 X/Y 与 W 按键的负号不完全等同于操作者感受，W 目前产生负 X。先沿用经实测的操作方向，不凭注释机械改号。旋转正方向也以统一模型和实测为准。

### 4.3 对称 X 型的矩阵

沿用当前分配器的列符号，`c=cos45°`，`l` 为经过几何和方向验证的正有效力臂：

```text
J = [ -c, +c, l ]   LF
    [ +c, +c, l ]   RF
    [ -c, -c, l ]   LB
    [ +c, -c, l ]   RB

轮缘速度 u = J * [vx, vy, wz]^T
底盘合力矩 W = J^T * 轮端力 f
```

四轮轮缘速度为 `u0..u3` 时：

```text
vx = (-u0 + u1 - u2 + u3) / (4*c)
vy = ( u0 + u1 - u2 - u3) / (4*c)
wz_encoder = (u0 + u1 + u2 + u3) / (4*l)
```

对称情况下最小范数分配：

```text
f0 = -c*Fx/2 + c*Fy/2 + Mz/(4*l)
f1 =  c*Fx/2 + c*Fy/2 + Mz/(4*l)
f2 = -c*Fx/2 - c*Fy/2 + Mz/(4*l)
f3 =  c*Fx/2 - c*Fy/2 + Mz/(4*l)
```

当前几何初值 `l=(0.350/2+0.300/2)*c`，约 0.2298 m。它依赖轮子实际驱动方向，必须用纯转动测试核对。若轮位、安装角或参考中心不对称，应使用真实 `x_i/y_i/t_i` 构造 `J_i=[t_ix,t_iy,x_i*t_iy-y_i*t_ix]`，正反解使用同一矩阵。

不要复用含 `DEGREE_2_RAD` 的旧 `LF_CENTER/OMNI_L` 作为米制力臂。现有伪逆的统一 `lambda*I` 混合了平动和转动列的尺度；非对称通用实现需要合理归一化或加权，不能只凭一个 lambda 调手感。

用功率一致性检查模型：`W·v` 应与 `f·u` 相等。满足它只能证明数学一致，还需要实际方向测试。

### 4.4 轮速一致性与 RF 问题不能只看底盘平均速度

三轴外环控制的是三维底盘运动，不自动保证第四个冗余轮速完全符合模型。反馈可以在平均意义上接近目标，但某轮仍有接地、摩擦或打滑异常。

逐轮检查 `u_measured_i - J_i*v_est`；对上面的对称矩阵，理想情况下冗余残差 `u0-u1-u2+u3` 接近零。大残差提示运动学不一致，可能来自轮滑、轮子离地、机械阻力、方向错误或测量延迟，但它本身不能唯一定位故障轮。

纯 X 平动且不打滑时四轮轮缘速度的绝对值应接近；斜向或旋转时各轮目标本来就可能不同甚至为零。因此不能把“RF 在 W+A 时转”或“四轮不等速”孤立地当成故障证据，需要结合该动作的 J 目标、最终电流和轮速一起判断。

如果三轴跟速正常而 RF 在应转动的纯 X 测试中持续不动，不能直接宣告调试通过。先排查机械、标定、限幅和符号。必要时再设计经过验证的冗余轮速协调/滑移降额，不直接把四轮速度 PID 和三轴力外环同时全增益叠加。

## 5. 先标定电流到输出力矩

### 5.1 当前系数存在的风险

源码使用：

```c
#define FORCE_MOTOR_KT_NM_PER_A 0.30f
#define FORCE_GEAR_RATIO 19.0f
#define FORCE_DRIVE_EFFICIENCY 0.85f
#define FORCE_CURRENT_RAW_PER_A (16384.0f / 20.0f)
```

必须查明 `0.30` 是转子轴 Kt 还是减速后输出轴的等效系数。如果已经是输出轴参数，再乘 19 就重复计算。不能只根据同一参数反算出的日志力值判断它正确，也不能未经确认直接改成 `0.016`，这可能大幅提高电流。

命令 raw 和反馈 raw 的电流刻度分别查 C620/M3508 资料，不能默认完全一致。母线电流、相电流、驱动器返回的转矩电流不是同一物理量。

### 5.2 推荐标定输出端等效系数

推荐记录每轮 `Kout_i`，单位 N·m/A。下文不再额外乘减速比和效率：

```text
T_out = Kout_i * I_A
f_i = T_out / r
I_cmd_raw = f_i * r / Kout_i * RAW_PER_A_CMD
```

操作顺序：

1. 轮组可靠固定，输出轴安装长度 L 的力臂，用测力装置测垂直作用力 F；禁止手抓轮胎堵转。
2. 采用短时、受限电流，从最低可测水平开始；设置硬件急停和温度保护。
3. 记录 `T=F*L`、电流指令、反馈电流、方向、温度、电源电压和保持时间。
4. 正反方向各至少 5 个工作点，重复至少 3 次。不要超过器件允许工况，不长时间堵转。
5. 拟合斜率 `Kout = delta(T)/delta(I_A)`；分别记录截距、正反不对称和重复误差。
6. 截距不要硬塞进 Kout：零偏、静摩擦、传动损耗分别记录。若斜率非线性严重，应缩小适用范围或使用经过验证的模型。
7. 四轮分别标定，再用相同受限电流核对差异。静态输出轴标定不能保证高速效率和动态地面力同样准确。

没有输出力矩测量时，只能使用有来源的手册参数做保守初值，暂时关闭质量/加速度前馈、估算力积分和大电流测试。外环可以先调，但此时 N 的物理准确度未验证。

### 5.3 电流零偏

禁用驱动、稳定温度、采集至少数秒真实反馈，统计每轮均值、噪声和温漂。零偏应来自实际无力矩状态，不从带负载时的维持电流直接扣除。源码里四路固定偏置也要重新核对。

对反馈：`I_A=(feedback_raw-offset_raw)/RAW_PER_A_FB`。

对命令：`I_A=command_raw/RAW_PER_A_CMD`，通常不把反馈零偏加到命令上。

### 6.3 验证与故障分支必须随模式一起改

当前 `ChassisControlProtocolValid()` 对非速度模式主要检查 `fx_ref/fy_ref/mz_ref`。新增模式后必须：

1. 白名单拒绝未知 `control_mode` 和非法 `chassis_mode`。
2. 新模式检查版本，以及有限且在 SI 上限内的 `vx/vy/wz/offset_angle`。
3. 直接力矩/传感器模式检查力字段；传统速度模式也应增加 NaN 和量程检查，避免转整型前溢出。
4. 验证输入源、四轮反馈、IMU、裁判/电容数据各自新鲜度，不能只用一个“话题收到”布尔量。
5. 模式改变、急停、解除故障都复位新外环、滤波状态和所有电流历史；在正常模式切换时用当前实测速度初始化参考，实现受限过渡。
6. 非运动模式到运动模式之间即使都是 CURRENT_LOOP，也要复位外环；现有 `SetChassisOuterLoop()` 只根据外环类型变化判断，不能代替模式状态机。
7. 故障输出直接清零并 `DJIMotorStop()`，不得经过普通电流斜坡。恢复必须重新解锁。

## 7. 核心参考代码：SI 速度 PI 输出合力，再分配电流

下面是一个不依赖 STM32 的完整 C 计算示例，便于先做离线测试。可以拆为 `.h/.c`，公开需要的接口；不是可直接刷入的完整底盘程序。

约定：

- 对称 X 型、同一米制矩阵；`sign[]` 已由实车验证。
- `kout[]` 已标定，命令 raw/A 独立确认；没有已知值时禁止启用对应参数配置。
- `mass_or_iz=[m,m,Iz]`；首次 P 调试 `ff_gain[]` 全部为零。
- 限流、功率、温度、启速和电流斜坡在适配层统一执行，不在各层重复执行。
- `MFTrackApplied()` 的参数是实际准备发送的最终电流，而非力反馈滤波值。它用于抗积分饱和，不是力闭环。
- 平动轮速估计在不打滑时有效，函数的数学有效返回值不表示传感器在线，在线检查在适配层。

```c
/* MF_CORE_BEGIN */
#include <math.h>
#include <stdint.h>
#include <string.h>

#define MF_C45 0.70710678f
#define MF_D2R 0.01745329252f

typedef struct {
    float radius_m;
    float gear_ratio;
    float moment_arm_m;
    float raw_per_a_cmd;
    float kout[4];
    float sign[4];
    float mass_or_iz[3];
    float ff_gain[3];
    float kp[3];
    float ki[3];
    float integral_limit[3];
    float wrench_limit[3];
    float velocity_limit[3];
    float accel_limit[3];
    float brake_limit[3];
    float tracking_gain;
} MFConfig;

typedef struct {
    float ref[3];
    float last_target[3];
    float integral[3];
    float requested[3];
    float applied[3];
    uint8_t integrate[3];
} MFState;

static float MFClamp(float x, float lo, float hi)
{
    return fminf(fmaxf(x, lo), hi);
}

static int MFPositive(float x)
{
    return isfinite(x) && x > 0.0f;
}

static int MFNonnegative(float x)
{
    return isfinite(x) && x >= 0.0f;
}

static int MFConfigValid(const MFConfig *p)
{
    if (p == 0 || !MFPositive(p->radius_m) ||
        !MFPositive(p->gear_ratio) || !MFPositive(p->moment_arm_m) ||
        !MFPositive(p->raw_per_a_cmd) ||
        !MFNonnegative(p->tracking_gain))
        return 0;
    for (unsigned i = 0; i < 4; ++i) {
        if (!MFPositive(p->kout[i]) ||
            !(p->sign[i] == 1.0f || p->sign[i] == -1.0f))
            return 0;
    }
    for (unsigned k = 0; k < 3; ++k) {
        if (!MFNonnegative(p->mass_or_iz[k]) ||
            !MFNonnegative(p->ff_gain[k]) ||
            !MFNonnegative(p->kp[k]) || !MFNonnegative(p->ki[k]) ||
            !MFNonnegative(p->integral_limit[k]) ||
            !MFPositive(p->wrench_limit[k]) ||
            !MFPositive(p->velocity_limit[k]) ||
            !MFPositive(p->accel_limit[k]) ||
            !MFPositive(p->brake_limit[k]))
            return 0;
    }
    return 1;
}

static int MFVectorValid(const float *v, unsigned count)
{
    if (v == 0)
        return 0;
    for (unsigned i = 0; i < count; ++i)
        if (!isfinite(v[i]))
            return 0;
    return 1;
}

static void MFReset(MFState *s, const float measured[3])
{
    memset(s, 0, sizeof(*s));
    if (MFVectorValid(measured, 3))
        memcpy(s->ref, measured, sizeof(s->ref));
}

static int MFEstimateEncoderVelocity(const MFConfig *p,
                                    const float motor_dps[4],
                                    float velocity[3])
{
    float u[4];
    if (!MFConfigValid(p) || !MFVectorValid(motor_dps, 4))
        return 0;
    for (unsigned i = 0; i < 4; ++i)
        u[i] = p->sign[i] * motor_dps[i] * MF_D2R /
               p->gear_ratio * p->radius_m;
    velocity[0] = (-u[0] + u[1] - u[2] + u[3]) / (4.0f * MF_C45);
    velocity[1] = ( u[0] + u[1] - u[2] - u[3]) / (4.0f * MF_C45);
    velocity[2] = (u[0] + u[1] + u[2] + u[3]) /
                  (4.0f * p->moment_arm_m);
    return MFVectorValid(velocity, 3);
}

static void MFWrenchToCurrent(const MFConfig *p, const float w[3],
                             float raw[4])
{
    const float x = MF_C45 * w[0] * 0.5f;
    const float y = MF_C45 * w[1] * 0.5f;
    const float z = w[2] / (4.0f * p->moment_arm_m);
    const float f[4] = {-x + y + z, x + y + z,
                       -x - y + z, x - y + z};
    for (unsigned i = 0; i < 4; ++i)
        raw[i] = p->sign[i] * f[i] * p->radius_m /
                 p->kout[i] * p->raw_per_a_cmd;
}

static void MFCurrentToWrench(const MFConfig *p, const float raw[4],
                             float w[3])
{
    float f[4];
    for (unsigned i = 0; i < 4; ++i)
        f[i] = p->sign[i] * raw[i] / p->raw_per_a_cmd *
               p->kout[i] / p->radius_m;
    w[0] = MF_C45 * (-f[0] + f[1] - f[2] + f[3]);
    w[1] = MF_C45 * ( f[0] + f[1] - f[2] - f[3]);
    w[2] = p->moment_arm_m * (f[0] + f[1] + f[2] + f[3]);
}

static int MFStep(MFState *s, const MFConfig *p,
                  const float target[3], const float measured[3],
                  float dt, float current_request[4])
{
    float limited[3];
    if (!MFConfigValid(p) || !MFVectorValid(target, 3) ||
        !MFVectorValid(measured, 3) || !isfinite(dt) ||
        dt < 0.001f || dt > 0.020f) {
        memset(current_request, 0, 4 * sizeof(float));
        MFReset(s, 0);
        return 0;
    }
    for (unsigned k = 0; k < 3; ++k) {
        const float goal = MFClamp(target[k], -p->velocity_limit[k],
                                    p->velocity_limit[k]);
        const uint8_t released = fabsf(goal) < 1.0e-5f;
        const uint8_t reversed = goal * s->last_target[k] < 0.0f;
        const uint8_t decelerating =
            released || (goal * s->ref[k] < 0.0f) ||
            (fabsf(goal) < fabsf(s->ref[k]));
        const float rate = decelerating ? p->brake_limit[k] :
                                         p->accel_limit[k];
        const float old_ref = s->ref[k];
        s->ref[k] += MFClamp(goal - old_ref, -rate * dt, rate * dt);
        const float accel_ref = (s->ref[k] - old_ref) / dt;
        const float error = s->ref[k] - measured[k];
        if (released || reversed || p->ki[k] == 0.0f)
            s->integral[k] = 0.0f;
        s->integrate[k] = !released && p->ki[k] > 0.0f;
        if (s->integrate[k])
            s->integral[k] = MFClamp(s->integral[k] + p->ki[k] *
                                     error * dt,
                                     -p->integral_limit[k],
                                      p->integral_limit[k]);
        s->requested[k] = p->ff_gain[k] * p->mass_or_iz[k] * accel_ref +
                          p->kp[k] * error + s->integral[k];
        limited[k] = MFClamp(s->requested[k], -p->wrench_limit[k],
                                               p->wrench_limit[k]);
        s->last_target[k] = goal;
    }
    MFWrenchToCurrent(p, limited, current_request);
    if (!MFVectorValid(current_request, 4)) {
        memset(current_request, 0, 4 * sizeof(float));
        MFReset(s, 0);
        return 0;
    }
    return 1;
}

static int MFTrackApplied(MFState *s, const MFConfig *p,
                          const float final_raw[4], float dt)
{
    if (!MFConfigValid(p) || !MFVectorValid(final_raw, 4) ||
        !isfinite(dt) || dt < 0.001f || dt > 0.020f)
        return 0;
    MFCurrentToWrench(p, final_raw, s->applied);
    if (!MFVectorValid(s->applied, 3))
        return 0;
    for (unsigned k = 0; k < 3; ++k) {
        if (s->integrate[k])
            s->integral[k] = MFClamp(s->integral[k] +
                p->tracking_gain * (s->applied[k] - s->requested[k]) * dt,
                -p->integral_limit[k], p->integral_limit[k]);
        else
            s->integral[k] = 0.0f;
    }
    return 1;
}
/* MF_CORE_END */
```

### 7.1 如何初始化配置，不提供伪装成实车参数的默认值

从标定表填 `radius_m/gear_ratio/moment_arm_m/raw_per_a_cmd/kout/sign`。`kp/ki` 单位不同于现有四轮 PID：

```text
平动 Kp：N / (m/s)
平动 Ki：N / ((m/s)*s)
旋转 Kp：N·m / (rad/s)
旋转 Ki：N·m / ((rad/s)*s)
tracking_gain：1/s
```

第一轮设置 `ki=0`、`ff_gain=0`、启速补偿=0，不用 D；给每轴设置受限输出和积分上限。配置结构中零填充会导致验证失败，必须显式填完所有必需项。若该轴暂不控制，目标为零，但安全范围仍需配置有效值。

建议通过允许的最大低速误差来推导 P 初值，而不是复制常数：

```text
Kp_x 初值 <= 已标定安全合力上限 / 预期最大初始速度误差
例如只用于说明量纲：10 N / 0.2 m/s = 50 N/(m/s)
```

示例不表示 10 N 和 50 适合你的实车；必须由电流限值、Kout、摩擦与供电确认。

本核心简化了三个方面：平动加速度逐轴限制，斜向加速度可能更大；未加入旋转坐标系动力学交叉项；零目标清积分，属于主动速度制动而非位置保持。第一阶段只测单轴。后续按平动向量模长统一限制速度/加速度/合力，在自旋平动时增加经过验证的耦合前馈。

### 7.2 底盘任务接入顺序

必须先估计反馈再控制，而不是在任务末尾才更新 `EstimateSpeed()`。

下面是接口级伪代码，`SafetyCheck/LimitAndPublish/StopAndReset` 等都需要实现，没有暗示工程已存在这些函数：

```text
接收命令；获取实际 dt
读取四轮反馈和 IMU 的一致快照，读取采样时间/序号
SafetyCheck：输入源、协议、轮反馈、IMU、供电、任务周期、故障锁存
若失败：清零最终 CAN 电流，DJIMotorStop，复位核心，等待重新解锁

检查模式变化，清状态；运动模式进入时用实测速度初始化参考
MFEstimateEncoderVelocity：得到 vx/vy/wz_encoder
若使用有效底盘 IMU：wz_feedback = gyro_z_dps * sign * pi/180
否则仅在批准的受限测试模式使用 wz_encoder
把云台系目标 vx/vy 转到底盘系（变换一次）
新模式生成跟随/自旋目标 wz，单位 rad/s
目标向量限幅
MFStep：生成请求电流
统一安全限流、斜坡、功率和温度处理，发布带 seq 的四轮请求
电机任务对最终待发送电流再次执行安全约束，组帧发送
回传匹配 seq 的最终电流，运动任务进行 MFTrackApplied
发布速度、力矩和保护状态；日志单独降采样
```

坐标变换可沿用当前数学形式，但方向通过云台 offset=0、90、180 deg 的实车测试确认：

```c
float theta = (offset_deg + trim_deg) * MF_D2R;
float body_vx = input_vx * cosf(theta) - input_vy * sinf(theta);
float body_vy = input_vx * sinf(theta) + input_vy * cosf(theta);
```

核心的目标和反馈都要是底盘系。旋转时目标在底盘系变化会影响参考加速度，第一版关闭前馈；后续高速自旋下按物理定义增加 `Fx=m*(dvx/dt-wz*vy)`、`Fy=m*(dvy/dt+wz*vx)` 等项，不把坐标旋转产生的变化全部误认为惯性加速度。

### 7.3 不要直接调用原版 `RunTorqueControl()` 执行新外环结果

原版还有：任务空间起步补偿、1500 raw 单轮补偿、弱轮速阻尼、零力死区、松键特殊制动、陀螺仪阻尼、按周期的电流斜坡。

新外环已经包含反馈制动。如果直接复用原版，会出现：

- 旧 3 N 死区吞掉小速度误差的修正。
- 一边速度外环要求维持速度，一边旧阻尼不断减小电流。
- 正反切换或制动电流被当成“启动命令”再次加补偿。
- 旋转 PI 和旧陀螺仪阻尼重复作用。
- 两套制动、两套斜坡和两套限幅互相影响，调参无法归因。

建议保留原 TORQUE 路径，新增一个仅负责“合力分配/换算”的执行接口和统一保护层。第一版新模式不要调用旧补偿函数；需要摩擦补偿时按第 9 节单独加入。

### 7.4 并发与抗积分饱和接入

200 Hz 运动任务和约 500 Hz 电机任务不是同步调用。不要让电机任务随时改写运动 PI 的结构体。

使用双缓冲/短临界区消息：请求带 `seq`，执行反馈带对应 `seq`、最终四轮电流、限幅比例和时间戳。运动任务读取稳定快照，在正确的请求上做追踪回算，避免把上一帧施加电流与当前未限幅力错误比较。

简化第一版可以在运动任务内完成全部输出约束并立即 `MFTrackApplied()`，但只有当底层不会再改变电流且命令有效发送时，这个回算才代表最终执行命令。比赛版底层若仍会降额，应按带序号反馈修正。丢帧、CAN 发送失败不能标记成已施加力矩。

模式改变时应发布清零帧、清除斜坡历史并确认执行模式；电机任务必须独立检查请求帧龄、急停和在线状态，防止运动任务卡住后继续发送旧电流。故障时状态复位和解锁策略不可省略。

## 8. 功率控制必须真正接到最终输出

### 8.1 推荐接法

保留 `DJIMotorInit()` 作为唯一电机注册和 CAN 发送所有者。把底盘功率策略改为只处理注册的四个底盘电机，不另建第二套反馈/发送对象。

在 `DJIMotorControl()` 中组织成：

```text
逐电机计算控制器输出 -> float final_current[]
把 stop/offline/NaN 对应通道置零
对底盘四通道统一限流、功率和温度降额
检查电机型号的命令范围、转成 int16_t
按 motor->message_num 填 CAN 数据
发送并回传四路最终电流与发送状态
```

处理底盘子集，不能让它限制云台、摩擦轮或拨弹电机。LF/RF/LB/RB 的模型顺序需要显式映射到 CAN ID 1/4/2/3，不能靠注册下标猜测。

旧 `PowerControl()` 的功率计算主要在速度环分支里进行，不能仅把初始化替换成 `PowerControlInit()` 就假定直接电流模式已正确限功率。审查它的单位、模式覆盖、停止逻辑、发送冲突和数组容量后才可能复用算法。

### 8.2 模型和标定

一种可验证的近似模型：

```text
P_predict_i = a_i * current_raw_i^2
            + b_i * speed_motor_radps_i^2
            + c_i * current_raw_i * speed_motor_radps_i
            + p0_i
```

系数应通过实测母线功率拟合，单位由输入决定；电流项、机械功率项和固定损耗分开。也可以采用基于输出轴转矩/转速的物理模型，但转子轴和输出轴只选一套，不能混乘减速比。

`24 V * abs(电机相电流)` 不是可靠的底盘母线功率模型。反馈电流乘固定电压也不能精确估计瞬态功率。

对四轮请求按统一比例 `s` 缩放，寻找满足预算的最大可行 s。驱动工况下可以对经过验证的单调模型用有界求解；再生制动时交叉项可能为负，不能未经分析用假定单调的二分。电池/电容/电调能否吸收再生能量必须确认，母线过压时不能盲目增加制动电流。

预算来自：最新裁判限制、缓冲能量策略、电容状态、供电能力和规则。裁判数据无效时采用经验证的安全预算或停机，不能把零初始化字段直接当成合法限制，也不能在比赛版无限制运行。

### 8.3 约束的优先级与回算

1. 急停/掉线/非法数据：立即零输出，优先于所有斜坡。
2. 器件电流、母线和温度硬约束：立即降额，必要时允许快速减小电流。
3. 正常力矩和功率预算：尽量统一缩放四轮，记录缩放比例。
4. 正常变化率限制：用 raw/s 乘实际 dt，不用固定每周期 600；它不能阻止硬保护立即降额。
5. 最终再检查全部约束，回算实际执行合力给抗积分饱和。

普通斜坡若逐轮独立，会暂时改变力矩方向；使用共同插值比例可以减小破坏，但约束变化/单轮故障时仍需安全优先。电流硬上限不能被斜坡保留的历史大电流绕过。

### 8.4 如何证明已接通

- 在同一受限速度命令下，降低预算，最终 CAN 电流和实测功率应相应变化。
- 高速、低速起步、松键制动、斜向、自旋、受限短时堵转都测试，不能只看速度环工况。
- 日志同时记录请求电流、最终 CAN 电流、反馈电流、模型功率、实测功率、预算和缩放比例。
- 比较真实裁判功率、缓冲变化和电容反馈，留出模型误差裕量。
- 功率受限时速度积分不能持续增长；恢复预算后不能突然冲车。

## 9. 启速、摩擦和制动：最后才加补偿

### 9.1 先用受限 P 外环启动

初次落地目标 0.1~0.2 m/s、加速度可从 0.3~0.5 m/s² 的范围选择，实际值按场地和实车安全能力确定。启动时速度误差产生驱动力；如果不启动，按以下顺序诊断：

1. 命令是否已进入新模式，目标是否正确。
2. 反馈是否在控制前更新，单位是否正确。
3. P 输出是否被力上限、死区、功率或斜坡压制。
4. 最终 CAN 电流是否正确，反馈电流是否跟随。
5. 实测静摩擦阈值是否超过输出能力；检查机械和换算系数。

不要立即恢复 1500 raw 再无限增大。能启动也不意味着启速逻辑正确，必须记录启动延迟、补偿退出、低速重复动作和温升。

### 9.2 加入可解释的摩擦前馈

先记录每轮正反方向启动电流和低速稳定运行电流，使用经标定的库仑/粘性摩擦前馈：

```text
I_ff_i = Ic_i * smooth_sign(目标轮缘速度_i)
       + B_i * 目标轮缘速度_i
```

在目标速度零附近设连续过渡，不在正常松键停车时固定加正向电流。对明显速度反向运动，摩擦补偿符号需要与实际运动/启动状态协调；简单按目标符号可能在换向制动时适得其反。

如果仍需启动脉冲，使用独立状态机：只在真正的非零目标启动沿触发、有限幅有限时、达到速度后平滑退出、失败锁存/有限次重试。制动或力矩修正反向不应重新触发启动补偿。

补偿加入后，抗积分饱和应区分目标任务力和额外摩擦电流，不让外环为了抵消补偿而积累相反积分。记录完整总电流，不只记录动力学分量。

### 9.3 松键为什么能够更及时停止

新模式松键后目标速度为零，参考按制动加速度受限下降；外环通过负速度误差产生制动力，靠近零速时制动力自然降低。

制动距离初估：`d=v0²/(2*a_brake)`，还要加采样、反馈滤波、通信与执行延迟造成的距离。制动能力受地面附着、功率/再生约束和机械冲击限制，不是 Kp 越大越好。

验证停止时分别测：输入松键时刻、参考降为零时刻、独立实测速度降到阈值时刻、最终距离。不能只看编码器零速，因为轮子锁住打滑时整车仍可能移动。

停止后持续有小正向力矩，应检查积分残留、启速重触发、前馈零点、坐标变换或按键状态，不继续提高反向制动掩盖问题。

参考斜坡还有一个边界：若松键时实际速度远低于尚未降下来的参考，简单速度 PI 可能短暂仍给出正向力矩。要求立即开始减速时，应在松键沿用可靠实测速度重建制动参考，或建立独立 BRAKE 状态并禁止同向驱动；制动状态同样受母线、附着和电流约束。上面的核心示例只提供基本参考斜坡，不包含完整比赛制动状态机，这个边界必须在适配层实现和测试。

## 10. 分阶段实车调试，每一阶段不过关就停在该阶段

### 阶段 0：版本、安全、基线

1. 记录源码和参数版本，建立旧速度模式的可回退固件。
2. 最新固件打印唯一标记，如 `MOTION_TORQUE_20261008_R1`；每次参数变化增加 revision。
3. 用旧速度模式完成 W/S/A/D、松键、换向和急停基线，记录速度/停车距离/功率。
4. 检查图传、遥控、电机掉线和重新解锁；轮子不接地时做故障注入。

验收：任何故障都能撤销旧输出；恢复不自动带旧非零命令启动；固件和源码一一对应。

### 阶段 1：方向、反馈单位与几何

1. 架空，小幅短时单轮电流实验，先断开其他电机输出，确认签名表。
2. 验证编码器转速到输出轮实际转速的减速比。
3. 手动或受限驱动做纯 X、纯 Y、纯旋转，核对 J 正反解。
4. 固定底盘/转云台、固定云台/转底盘，确认 IMU 来源。
5. 用外部观测确认坐标方向；四轮都转不代表车体方向正确。

验收：纯轴运动估计的非目标轴明显小于目标轴；正反方向一致；真实低速与编码器估计相符。架空速度估计只是轮缘运动学等效速度，不是底盘真的移动。

### 阶段 2：电流和转矩标定

按第 5 节完成四轮输出端斜率、电流刻度、零偏和机械阻力记录。未标定准确时将动力学前馈和力反馈积分关闭。

验收：标定有方向、误差、温度、适用范围；四轮显著差异有原因，不靠单个常数拍脑袋补齐。

### 阶段 3：离线测试计算核心

用固定输入测试下面各项，先不连接 CAN：

| 输入/条件 | 期望 |
| --- | --- |
| 四轮零速度 | 三轴估计为零 |
| 按 J 生成纯 X/Y/Z 轮速 | 反解还原该轴与量级 |
| 仅 Fx/Fy/Mz，各自正负 | 四轮分配再反算还原输入 |
| 任意 sign 组合 | 转换对称、正反算一致 |
| 已标定 Kout 不同 | 相同物理力需要不同 raw，回算仍正确 |
| dt=0、NaN、超时、非法 Kout | MFStep 失败、请求清零 |
| 模式复位 | 积分、旧目标、电流历史不遗留 |
| 输出持续限幅 | 积分有界，解除限幅不突冲 |
| 松键、目标反向 | 清除旧积分，参考受限变化 |

浮点比较允许小误差，例如相对误差 `1e-4`；不要直接 `==` 判断物理计算结果。反馈零偏、传感器在线和执行失败也需要适配层测试。

本次文档中的核心示例已完成以下离线检查，参数为合成测试参数，不是实车标定值：

- ARM GCC 使用 C11、`-Wall -Wextra -Werror` 完成语法检查。
- 主机 GCC 编译并执行 4000 组运动学、力矩正反解和功率一致性测试，包含不同轮端系数与方向符号。
- 非法配置、NaN、无效/超时 dt 导致请求清零。
- `Ki=0` 时即使输出限幅也不会通过回算产生隐藏积分。
- 简化一维质量-阻尼模型能跟踪目标速度，并在松键后制动。
- 持续限幅下积分有界，目标反向和状态复位测试通过。

这些结果只验证示例的部分数学和状态逻辑，不覆盖真实摩擦、打滑、CAN 延迟、功率模型、并发适配、传感器或比赛工况。

### 阶段 4：架空受限 P 外环

1. `Ki=0`、`Kd=0`、前馈=0、启速=0，开启受限电流和已验证功率约束。
2. 小目标、短时运行，确认误差符号正确；速度变大时 P 修正必须朝减速方向。
3. 检查零目标、目标反向、模式切换和急停。
4. 架空负载与落地不同，只验证符号/闭环方向，不在架空状态完成全部增益调参。

验收：无发散、无意外补偿脉冲、每一路反馈有效、停止/恢复顺序正确。

### 阶段 5：落地单轴 P 与松键制动

1. 设置受限的 0.1~0.2 m/s 测试速度，从最小可运行 P 开始。
2. W、S 各测试至少 10 次启动/保持/松键，A、D 同样测试。
3. 一次只改一个参数。先保证正确启动，再看超调、持续误差和停车。
4. 每轮参数变化可按约 10%~20% 小幅度调整；出现振荡/打滑/冲击立即退回。
5. 比较 LF/LB、RF/RB 的物理轮缘速度、最终电流和接地情况，不只比较电机原始数字。
6. 无积分时有少量稳态误差可以接受；先保证稳定和安全，不用积分掩盖错误单位。

验收：20 次连续启停不需拨轮、不出现 RF 持续零速、无持续颤动和启速反复撤力。停车性能在相同低速下不劣于基线，停下不反向爬行。

### 阶段 6：加积分、前馈与摩擦

1. P 稳定后逐步加入很小的 Ki，观察稳态误差和功率受限时积分。
2. 验证零目标清积分、换向清积分、模式切换清状态。
3. 加入标定后的摩擦补偿，重新测试低速和启停。
4. 最后加入 `m*a_ref`、`Iz*alpha_ref` 前馈，`ff_gain` 从零逐步提高，不默认设为 1。
5. 参数与整车重量、轴端 Kout 必须对应；明显超调时先区分模型过大、积分、滤波延迟，而不是一起减所有增益。

验收：负载变化可控；功率受限/解除后不冲车；零目标无残余驱动力；启动补偿平滑退出。

### 阶段 7：斜向、旋转与跟随云台

1. W+A、W+D 等斜向向量限幅，检查多轴耦合和电流共同缩放。
2. 低角速度旋转，对照编码器 wz 和真正底盘 IMU wz。
3. 小角度云台跟随：角度误差 -> 受限 rad/s -> 旋转速度 PI。
4. 自旋从低角速度逐渐增加，观察母线、温升、平动方向和滑移。
5. 最后做自旋中平动，关闭前馈验证基础，再逐项加入坐标耦合修正。

验收：旋转方向正确；云台单独转动不会被误判为底盘旋转；纯平动无持续偏航；跟随无来回摆动。

### 阶段 8：逐级速度、功率与负载

可按 0.2、0.5、1.0 m/s 等级逐步提高，是否继续加速由场地长度、停车距离和保护余量决定，不能照表直接升到高速。旋转速度独立逐级提高。

每一级都做：启动、持续、松键、换向、斜向、低预算、正常预算、电池高/低电量、冷热机、完整负载。出现限幅时间很长但速度达不到目标时，降低可达目标/加速度，不只增加 Ki。

验收：功率数据与最终输出一致；每一级停车区域足够；没有重复掉线/复位；日志中没有无解释的轮速丢失。

### 阶段 9：故障与耐久验收

在架空或受限低速安全条件下测试：输入断线、单轮反馈失效、IMU 超时、NaN、协议不符、任务超时、裁判/电容掉线、CAN 发送失败。不要带电随意拔高电流电源接头。

做符合目标比赛工况的连续运行，并覆盖弹丸/电池质量变化、轮胎磨损和地面变化。记录电机、电调、电池、接插件温升。故障注入后必须重新解锁，不自动恢复。

最后与旧速度模式做同条件 A/B 测试。不达标就保留旧模式比赛，继续受限调试，不因为功能名称是力控就强行使用。

## 11. 估算力闭环怎么加，以及什么时候不要加

### 11.1 在主驾驶稳定之后单独验证

建议新增独立实验模式 `CHASSIS_CONTROL_EST_FORCE_TRACK`，不要悄悄改变已有 TORQUE 的语义。传感器模式继续只接受真实传感器，不把“传感器失效自动改成估算力”当作无条件安全回退。

估算力反馈来自电机真实电流：

```text
I_feedback_A = (feedback_raw-offset_raw)/RAW_PER_A_FB
f_est_i = sign_i * I_feedback_A * Kout_i / radius
W_est = J^T * f_est
W_cmd = W_ref + PI_force(W_ref-W_est)
```

以下是接口示例，PID、限幅、复位、新鲜度和抗积分饱和需要配置后才能使用：

```c
float fx_cmd = fx_ref + PIDCalculate(&estimate_force_x, fx_est, fx_ref);
float fy_cmd = fy_ref + PIDCalculate(&estimate_force_y, fy_est, fy_ref);
float mz_cmd = mz_ref + PIDCalculate(&estimate_force_z, mz_est, mz_ref);
/* Allocate the limited wrench, then apply unified output protection. */
```

不要单纯删除 `ReadForceMeasurement()` 的传感器校验来接这个模式。应另建估算反馈函数，显式标记 ESTIMATE、独立校验四轮电流新鲜度、保留 SENSOR 模式原有保护。

`PIDCalculate()` 使用内部 DWT 间隔；新模式首次调用/长时间停用后要重新初始化时间基准。简单清 `Iout` 不会刷新 `DWT_CNT`。外环复位应同时清历史误差、输出、滤波项并更新计时。

估算反馈目前叠加驱动电流滤波、中值滤波和 `alpha=0.20` 的低通。总延迟不能忽略；力反馈修正要从低增益、无积分开始，用实测频响/阶跃选择带宽，不能假定在速度环与 C620 之间再放一层 PI 必然更好。

### 11.2 与启速和制动如何协调

启速额外电流会提高估算力，若力环仍把原始低力目标作为参考，会主动抵消启速补偿。松键主动制动需要非零反向力，若同时要求力环“保持零力”，也会互相抵消。

因此力环应跟踪明确的执行力矩目标，包括外环要求的制动力；摩擦/启动补偿是否属于目标必须在模型中定义。目标力要根据最终限流和功率能力处理，积分不能追踪一个永远不可达的上游值。

先在独立直接力跟踪实验中证明估算修正有效，再决定是否接入主驾驶。如果 C620 电流跟踪已足够好、额外外环没有改善误差却增加振荡/延迟，保留估算力作监测更合理。

### 11.3 地面力估计与接触模式

电流力矩还用于转子/轮组加速、传动损耗。估计接地驱动力需要考虑输出侧等效惯量、角加速度、摩擦和效率：

```text
f_ground_est = (T_output_est - J_equiv*alpha_wheel - T_loss)/radius
```

转子惯量折算到输出侧涉及减速比平方，单位和轴端必须统一；角加速度求导容易放大噪声。车体惯性测量得到的是净力相关量，也不能不区分地面阻力、碰撞力和坡度就当作电机牵引力反馈。

需要稳定推撞时单独设置低速接触模式：限速度、限力矩、限温、限持续时间、接触丢失保护、功率控制和解除条件。没有接触感知时，推力指令可能在阻挡消失后导致持续加速，不能无限保持。

## 13. 建议验收指标与比赛前检查

以下是起始验收目标，需根据旧速度模式基线和比赛任务调整。测量必须优先使用独立整车速度，而不只看轮速反解。

| 项目 | 建议目标/方法 |
| --- | --- |
| 低速启停 | W/S/A/D 每方向至少 20 次，不需拨轮，不反复抖动或间歇停转 |
| 速度误差 | 可先要求稳定后误差 <= max(0.03 m/s, 目标速度的 10%)，随后按基线收紧 |
| 超调 | 可先以 <= 15% 作目标；低速用绝对误差同时评价 |
| 方向一致性 | 纯平动非目标轴和偏航可控，正反与斜向均记录 |
| 松键停车 | 同功率、同初速度下停车时间/距离不劣于传统速度基线，停后不倒爬 |
| 功率 | 正式链路有效，模型与测量偏差已记录，缓冲/电容策略不违反规则 |
| 温升 | 完整工况运行后低于器件规定并有裕量，无接插件异常发热 |
| 模式切换 | 不遗留旧力矩/积分，不出现无界冲击 |
| 故障 | 任一关键反馈失效能够在定义的超时预算内撤力，不自动恢复旧命令 |
| 打滑 | 有独立观测/可验证检测及受限降额，不把轮速当真实地速 |

试验前列出最大允许速度、停车距离、输出电流、温度、母线范围和故障超时时间，超过任意一项立即中止。

最终检查：

- [ ] 最新固件标记、参数表和当前源码对应。
- [ ] 四轮机械、方向、SI 单位和 J 模型验证完成。
- [ ] 底盘 IMU 来源、方向、零漂和新鲜度通过。
- [ ] 转矩换算有标定记录，轴端没有重复乘减速比。
- [ ] 编码器速度估计与独立实测对照通过。
- [ ] 运动 P/PI 外环、加减速、松键制动分别通过。
- [ ] 启速/摩擦补偿非必须时关闭，必须时有状态机和失败保护。
- [ ] 正式功率限制真正修改最终 CAN 电流，直接电流模式也覆盖。
- [ ] 最终执行电流用于抗积分饱和，没有不可达目标持续积分。
- [ ] 图传、遥控、CAN、电机、IMU、裁判/电容异常测试通过。
- [ ] 自旋平动、云台跟随、多轴限幅和负载变化通过。
- [ ] 满足目标工况耐久、温升和供电测试。
- [ ] 相同条件 A/B 性能至少达到旧速度模式基线。

## 15. 推荐现在就做的前三件事

1. 确认 A 板安装位置、四轮实际方向和 Kt 的轴端来源，停止继续单纯提高 1500 raw 启速补偿。
