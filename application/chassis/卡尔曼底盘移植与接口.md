# 卡尔曼底盘移植与接口

版本 `fw=20261111 frame=18`。现车参数、硬件采样和通用运动学分开，复用同一套四维 KF。支持四麦轮、四全向轮和四模块舵轮；单板与双板使用相同的估计/控制内核。每块 MCU 一个底盘实例，不支持在同一 MCU 同时创建多个底盘。

项目配置默认 `direct_translation=1`，在轮速能力内直接使用收到的平移速度，跳过 `max_velocity` 截顶和 `velocity_slew` 斜坡。`ChassisMotionConfigDefault()` 的通用默认值为0，按这两个参数生成平移参考。旋转限幅与斜坡、轮速能力约束、电流约束及停止条件继续生效。

frame17 新增独立补偿许可。自定义配置应先调用 `ChassisMotionConfigDefault()`，再按平台覆盖正数 `control_stable_s/control_velocity_max/control_accel_residual_max/control_ramp_s`。`ChassisMotionGetObservationState()` 可读取 `control_ready`、阻止原因、稳定时间、渐入比例和残差；`valid` 恢复不再直接许可追加。公共444字节状态及通信布局不变。默认仍为SHADOW，保护值和阶段边界见[第三十九次架空对照及独立补偿许可](调试记录/20261110_第三十九次架空对照与frame17独立补偿许可.md)。软件编译通过不代表对应轮型/板卡已实车通过。

frame16 按用户确认的四个全向轮外径145 mm，将工程 `RADIUS_WHEEL` 从60改为72.5 mm，项目适配器统一传入各轮0.0725 m。通用 `ChassisMotionConfigDefault()` 的0.06 m仅为移植示例，开发者必须用本车实测几何覆盖；不能把本车轮径当作其他麦轮/舵轮的通用尺寸。当时4000旧旋转档对应约6.575 rad/s；改6000将超过9 rad/s总上限。日志布局沿用frame15，详见[145 mm轮径标定修正](调试记录/20261108_第三十六次145mm轮径标定修正.md)。

现车默认继续 `MC_SHADOW`：估计和候选补偿参与记录，实际轮速不叠加 KF 补偿。frame15 在 frame14 时基/恢复检查上增加窗口内加速度积分残差拒绝、融合速度与轮速差异检查，并记录拒绝来源；姿态 EKF 的强制重捕获需要独立底盘静止许可。这些软件保护尚需实车验证；没有新增完整防滑/牵引力控制。功率控制仍保持原工程现状。

frame15 配置新增正数 `velocity_innovation_max`（默认 0.04 m/s），自定义配置应先调用 `ChassisMotionConfigDefault()` 再覆盖参数。`accel_consistency_max_dv` 用于积分残差，前者用于融合速度差，两者都只是观测冲突界限，不能判断打滑。窗口内残差超限立即拒绝；拒绝后必须完成整个 `accel_consistency_window_s` 的一致窗口，再积累恢复样本。公共历史状态仍为444字节；OBS 新增 `dv_now_mmps`、`v_res_mmps`、`reject_reason`，其中原因 1=窗口内残差、2=完整窗口残差、4=融合速度差。`rejects` 为拒绝事件累计，包含早期拒绝，不能与 frame14 的完整窗口次数直接比较。

INS 的 `att_flags` 新增位32（独立静止许可允许强制重捕获）、64（正在强制重捕获）。正常预测/通过检验的重力更新不依赖静止许可；连续拒绝后的强制校正才需要底盘上报新鲜的静止许可、IMU角速度小于0.05 rad/s以及连续500 ms确认。独立使用姿态库的平台通过 `IMU_QuaternionEKF_SetGravityRecoveryAllowed()` 每周期提供可信许可，缺省关闭强制重捕获；本工程沿用 `INS_SetChassisStill()` 接口。

## 1. 文件与职责

| 文件 | 职责 |
| --- | --- |
| `modules/chassis_motion/kinematics.h/.c` | 轮型、逐轮几何/标定、正逆解、轮速能力约束、舵轮角度优化；只依赖 C 标准库 |
| `modules/chassis_motion/chassis_motion.h/.c` | 配置校验、轮速/IMU 观测、固定 N 系 KF、G 系速度补偿、超时与恢复、日志队列 |
| `modules/chassis_motion/motion_port.h/.c` | 新平台的入口：读取一致性快照，运行 Update/Control，输出驱动轮与转向轮目标 |
| `application/chassis/chassis_setup.c/.h` | 装配轮型和车型参数，调用弱覆盖，再配置运动内核 |
| `config/config.c/.h`、`config/build_config.h` | 车辆参数、安装标定和编译组合校验 |
| `chassis.c` | 当前 DJI 电机、INS、发布订阅/CAN 命令、遥控三种模式和舵轮硬件钩子 |

新平台可只使用运动学、内核、port 和现有 `kalman_filter`/矩阵库，不需要链接 `chassis.c`、DJI、INS、CAN 或整车配置文件。当前 ARM 内核的短临界区使用 CMSIS 中断指令；移植到其他 CPU 时需替换 `Lock/Unlock`。`MC_HOST_TEST` 仅供无并发的主机测试。KF 首次配置时沿用现有内存分配器，周期运行不分配内存。

## 2. 板型与 IMU 来源

通过 Make 的 `EXTRA_DEFS` 选择一个板型，由 `config/build_config.h` 校验。没有定义时默认 `ONE_BOARD`；冲突定义会编译报错。

| 板型 | 本板初始化与执行 | 运动估计 IMU |
| --- | --- | --- |
| `ONE_BOARD` | CMD、云台、发射、底盘 | 当前默认共用随云台转动的本板 IMU；可选择固定底盘安装 |
| `CHASSIS_BOARD` | 底盘、本地 INS、板间 CAN | **底盘板本地 IMU**，不使用云台板发来的 IMU |
| `GIMBAL_BOARD` | CMD、云台、发射、本地 INS、板间 CAN | 本板 IMU 服务云台；本板不运行底盘 KF |

双板底盘侧强制 `MC_IMU_ON_GIMBAL=0`，错误配置会编译报错。云台板发送旧的速度/模式/相对 YAW 命令；底盘板结合本地轮速、相对 YAW 和本地 IMU 完成估计。两块 MCU 的系统时钟不需要相同起点：命令年龄使用**完整 CAN 消息通过 CRC 时的本地接收时间**。只有新完整消息会刷新时间；反复读取旧消息、半包和坏 CRC 都不会刷新。

当前板间接线为云台板 CAN1 ↔ 底盘板 CAN2：命令 ID `0x312`，反馈 ID `0x311`。收发双方须使用同版压缩协议；本次没有把大尺寸 IMU 快照塞进 CAN 协议。底盘板 CAN1 仍用于四个 DJI 驱动电机，映射 LF=1、RF=4、LB=2、RB=3。接入新车时须同时核对总线、ID 和机械轮位。

单板且 IMU 固定在底盘时，使用 `-DMC_IMU_ON_GIMBAL=0`。本地 INS 的杆臂按传感器轴向测量，配置 `MC_CHASSIS_IMU_LEVER_X_M/Y_M/Z_M`；默认全零。双板底盘同样使用这组参数，绝不会继承现车云台的 8.4 cm/3.7 cm 杆臂。云台安装继续使用 `MC_IMU_LEVER_SENSOR_*`。安装轴映射和航向安装角仍需在 INS/项目采样适配中标定，不能只改杆臂。

现有编码器辅助 YAW 零偏学习依赖单板的本地云台反馈与底盘静止许可，双板未新增远端编码器辅助学习链；它不是底盘 KF 正常工作的前提。

## 3. 单位和坐标约定

通用 API 使用右手系：B.x 向前，B.y 向左，B.z 向上，正 YAW 从上方看逆时针。N 是启动后固定的导航系，G 是平移命令参考系，可以是云台、操作员固定朝向或 B 本身。

| 数据 | 含义/单位 |
| --- | --- |
| 所有四轮数组 | 固定顺序 LF、RF、LB、RB；舵轮为四个模块的对应顺序 |
| `x_m/y_m` | 模块相对底盘参考中心的位置，m；默认 LF 位于 (+x,+y) |
| `radius_m/gear_ratio` | 有效滚动半径，m；减速比 = 电机转速 / 轮轴转速，均须 >0 |
| `motor_dps` | 驱动电机转子角速度，**deg/s**，不是 RPM 或轮轴 rad/s |
| `motor_sign` | 电机正方向到模型滚动正方向的映射，仅 ±1；同时作用于反馈和输出 |
| `velocity_g_mps/omega_radps` | G 系平移 m/s、底盘绕中心角速度 rad/s |
| `theta_bg` | `psi_GN - psi_BN`，rad，表示 G 相对 B 的朝向；G=B 时置零 |
| `psi_imu_n` | IMU 所代表参考系的 N 系平面航向，rad，已经修正安装方向 |
| `accel_n` | 去重力后的导航系运动加速度，m/s²；不得填原始比力 |
| `imu_center_n` | 在传感器采样频率完成三维杆臂校正后的中心加速度，m/s² |
| `omega_imu/imu_gyro_rad` | 航向角速度 rad/s、传感器三轴角速度 rad/s |
| `steer_rad` | **实测**滚动正方向在 B 系的方位角，rad；0 向前，π/2 向左 |
| 所有 `*_time_us` | 同一 MCU 单调微秒时钟低 32 位；用无符号差值处理正常回绕 |
| `*_seq` | 实际采样/接收序号；旧样本不能每次读时伪造新序号/时间 |
| 电流字段 | 驱动器原始电流单位，与 `current_limit` 保持一致；只用于饱和诊断 |

`imu_on_gimbal=0` 时航向就是 B 航向：`psi_BN=psi_imu_n`；为 1 时是 G 航向：`psi_BN=psi_imu_n-theta_BG`。云台 IMU 随 PITCH 转动时，传入其水平前向的航向，不能直接把倾斜传感器 Z 角速度当作 YAW 角速度。

`ChassisMotionConfigDefault()` 的 `algebra_y_sign=center_y_sign=+1`。新平台保持 +1。当前老车的命令 +Y 向右、INS 使用历史 N 轴约定，反射只放在项目适配层；麦轮/舵轮的项目入口会把旧协议的 +Y 向右换成通用 +Y 向左。不要把老车的 `MC_J_ROWS` 或 -1 反射直接复制到新车。

## 4. 轮型与逐轮标定

现工程编译时选择 `CHASSIS_DRIVE_OMNI_X`、`CHASSIS_DRIVE_MECANUM`、`CHASSIS_DRIVE_SWERVE` 之一；缺省为原全向轮。通用 API 的类型为：

| 类型 | 模型 |
| --- | --- |
| `CK_OMNI_X` | 四个 ±45° 滚动方向的全向轮；具体正方向见 `ChassisKinematicsProfile` |
| `CK_MECANUM_X` | X 布局麦轮；滚动线速度行的平移系数 `[1,-1]、[1,+1]、[1,+1]、[1,-1]` |
| `CK_SWERVE` | 四驱动 + 四转向模块；逐模块位置、实测舵角参与计算 |
| `CK_CUSTOM` | 自定义 4×3 固定轮矩阵，可支持其他四固定轮排布；矩阵必须满列秩 |

固定轮矩阵满足 `wheel_mps = rows × [vx_B, vy_B, omega_B]`。对于有滚动方向 `(dx,dy)` 的轮，角速度列为 `-dx*y+dy*x`；麦轮还包含滚子约束，不能把麦轮直接当作普通轮沿舵角投影。改变固定轮布局后应重建矩阵，而不是只改 `x_m/y_m`；`Profile()` 会按给定轴距/轮距生成矩阵。

驱动反馈换算：`wheel_mps = motor_dps × motor_sign × π/180 × radius_m / gear_ratio`。如果驱动器已经输出轮轴角速度，减速比应为 1；如果驱动层已经反转坐标，勿再次反转。各轮允许不同半径、减速比、符号和最高转速。

现工程可新建一个加入编译的适配文件，覆盖弱配置钩子，无需改 KF 内核。例如在已选择麦轮的项目中：

```c
#include "chassis_setup.h"

void ChassisMotionCustomizeConfig(ChassisMotionConfig *c)
{
    ChassisKinematicsProfile(&c->wheels, CK_MECANUM_X,
                             0.42f, 0.36f, 0.076f, 19.0f);
    c->wheels.motor_sign[1] = -1.0f; /* 示例，必须按实际安装确认 */
    c->wheels.motor_sign[3] = -1.0f;
    c->direct_translation = 0; /* 使用下面的平移限幅及配置中的速度斜坡 */
    c->max_velocity = 1.5f;
    c->phase_lead_s = 0.0f; /* 新车先不套用现车的 13.5ms 辨识结果 */
    c->initial_mode = MC_SHADOW;
}
```

钩子在 `ChassisMotionInit()` 的默认参数生成后、配置校验前调用。此路径的轮型须与项目编译选择一致；板型/IMU 安装仍通过项目宏选择，因为采样适配、INS 初始化和驱动也要匹配。`ChassisMotionConfigure()` 可用于新平台直接配置；只在启动或驱动器已禁止输出、控制/日志任务停止访问时调用，失败返回 0，并撤销内核的有效几何。不要把它当作控制周期中的实时调参函数。

## 5. 舵轮驱动接口

舵轮里程计使用实际舵角，把每轮实测有符号线速度变为 B 系二维速度，再用模块刚体位置做最小二乘。四轮全部平行时也能估计二维平移与转速；不得用目标舵角替代实测角。

指令分配生成模块期望速度向量，并选择离实测角最近的目标；转角超过 90° 时翻转驱动方向。默认启用 `steer_cosine_compensation`，按转向误差余弦降低驱动，减少舵向尚未到位时的横向拖拽；可在标定后显式关闭。静止时保持实测舵角。目标是接近实测角的连续角，转向驱动器必须正确处理跨 ±π、多圈角和机械限制。当前模型假定模块可连续旋转，未实现有限转角关节的路径规划。

沿用 `chassis.c` 时，在自己的硬件文件中实现以下两个同名函数，覆盖弱默认实现：

```c
#include "chassis.h"

uint8_t ChassisReadSteeringFeedback(float angle_rad[4],
                                    uint32_t time_us[4], uint8_t *online_mask);
uint8_t ChassisApplySteeringTargets(const float angle_rad[4], uint8_t enabled);
```

读取函数只复制驱动器缓存的校准舵角、各轮实际更新时间和在线掩码；全部在线为 `0x0F`，失败返回 0。它在快照短临界区内调用，不能等待总线、发送请求或阻塞。舵角零位、减速比、符号、绝对编码器多圈拼接在硬件层完成。

输出函数应将四个目标交给实际转向电机角度环/轨迹控制器。`enabled=0` 时按硬件要求禁止输出，忽略角度参数，不能把零数组当作强制回正命令。使能时四个目标均成功接受才返回 1；返回 0 会撤销本周期四驱动轮参考。默认弱函数返回 0，因此只打开舵轮宏不会直接驱动车辆。转向电机 ID、类型、限流和驱动注册由接入者实现，框架没有假定一定使用 DJI 转向电机。

任一舵角非法、离线、超过 `sample_max_us`，或与对应驱动轮时间相差超过 `sample_skew_us`，内核退出原因为 `MC_EXIT_STEERING`，驱动输出归零；现工程还会停止驱动电机并调用禁止转向输出。恢复后重新积累估计有效样本。缺失/过期舵角不能用旧角度继续驱动，`MC_BASELINE` 同样检查舵角。

## 6. 新平台通用接入

`ChassisMotionPort` 只有上下文、快照读取和输出两个回调；驱动类型、传感器型号、CAN/串口/共享内存方式均由平台决定：

```c
#include "motion_port.h"

/* 实现由平台提供：只读已发布的快照；write必须处理enabled=0。 */
extern uint8_t BoardRead(void *ctx, uint32_t now_us, ChassisMotionInput *in);
extern void BoardWrite(void *ctx, const ChassisWheelCommand *out, uint8_t enabled);

static const ChassisMotionPort port = {0, BoardRead, BoardWrite};

uint8_t MyChassisInit(void)
{
    ChassisMotionConfig c;
    ChassisMotionConfigDefault(&c, CK_SWERVE);
    ChassisKinematicsProfile(&c.wheels, CK_SWERVE, .42f, .36f, .06f, 19.0f);
    c.imu_on_gimbal = 0; /* 本地底盘IMU */
    c.initial_mode = MC_SHADOW;
    return ChassisMotionConfigure(&c);
}

void MyChassisTick(uint32_t now_us, float vx, float vy, float omega, uint8_t enabled)
{
    ChassisMotionCommand command = {{vx, vy}, omega, enabled, 0};
    (void)ChassisMotionStep(&port, now_us, &command);
}
```

这是接口层示例，`BoardRead/BoardWrite` 必须与真实硬件绑定；输入输出的可执行参考见 `tests/chassis_portability_test.c`。新工程需要编译 `modules/chassis_motion/` 下的 `kinematics.c`、`chassis_motion.c`、`motion_port.c` 和 `modules/algorithm/kalman_filter.c`，并链接矩阵库与 libm。沿用本工程的 `ChassisMotionInit()` 和弱配置钩子时，再加入 `application/chassis/chassis_setup.c` 与 `config/config.c`。

读取回调每周期清零快照后填入：

1. 四驱动电机反馈、真实序号/时间、在线掩码；舵轮再填四个实测舵角及时间/在线掩码。
2. IMU 实际采样序号/时间、航向、有效位、去重力运动加速度，以及 `use_center_accel=1` 时的中心加速度和有效位。默认配置使用这个已做三维杆臂补偿的分支，中心位无效会禁止主动补偿。
3. 相对朝向 `theta_bg`，及命令到达当前 MCU 后的真实年龄 `cmd_age_us`。G=B 时可置 theta 为 0，但仍须正确填写命令年龄。
4. 有电流反馈/限流诊断时填电流字段；无该功能可置零。其他姿态、原始 IMU 字段用于诊断，按注释单位填写。

`ChassisMotionStep` 的 `now_us` 是本周期计算时刻，作为快照截止时间；读取回调应返回不晚于该时刻的一致性缓存。未来时间戳会按无符号年龄被拒绝。读取失败、命令非法/过期、驱动轮离线/过期、异常 dt、非法几何或无效舵角都会通过 `write(..., enabled=0)` 发出零驱动参考。`write` 还应落实驱动器真正的使能/停止和自身看门狗；无输出回调时 Step 返回 0，无法替硬件执行停止。

返回值表示**估计有效**，不表示电机使能。IMU/姿态不可用会撤销主动补偿，基准速度链可继续在命令和轮/舵反馈有效时运行；不能因为 KF 无效就假定整车已经停下。`direct_translation=1` 时普通平移命令回零会立即清零平移参考，为0时按 `velocity_slew` 归零。急停/禁止输出立即清零驱动参考。

也可直接依次调用 `ChassisMotionUpdate → ChassisMotionControl → ChassisMotionGetWheelCommand → ChassisMotionRecord`，由项目自行检查命令和执行器使能；当前 `chassis.c` 使用此方式。不要在同一周期再调用 Step，也不要从两个任务同时运行内核。`Control` 的 `control_key=1` 标记自旋工况，允许相位补偿，并在 `config.rotation_priority=1` 时启用严格旋转优先；普通模式用 0。通用 Step 的 `command.rotation_priority` 对应这个工况标记，实际分配还由 config 控制。现车项目默认 `MC_WHEEL_LIMIT_ROTATION_PRIORITY=0`，超限时等比例降低平移和旋转，保留移动能力；通用库独立默认仍为旋转优先。`ChassisMotionForward/Inverse` 是旧固定轮兼容函数，舵轮使用带实测舵角的 `ChassisKinematicsObserve/Command`。

## 7. 参数与诊断接口

| 参数组/接口 | 需要接入者确认的内容 |
| --- | --- |
| `wheels` | 轮型、轮位、有效轮径、减速比、编码器方向、最高转子速度、舵角标定 |
| `imu_on_gimbal/imu_follows_pitch` | IMU 参考系和是否随俯仰转动；俯仰随动须提供三维校正 |
| `use_center_accel/center_y_sign` | 是否直接消费三维中心加速度；新平台中心 N 系使用 +1 |
| `imu_offset_m/yaw_center_m` | 平面兼容分支的 IMU 杆臂、云台中心相对底盘中心的位置，右手参考系中的 m |
| `accel_bias_n/r_velocity/r_accel/q_jerk` | 加速度零偏、轮速观测方差、加速度观测方差、连续白 jerk 谱密度，必须依据目标车辆数据辨识 |
| `direct_translation` | 项目默认1，平移参考立即跟随可行目标；通用默认0，启用 `max_velocity/velocity_slew` |
| `max_velocity/velocity_slew` | `direct_translation=0` 时的平移速度模长上限及变化率上限；为1时跳过，配置值仍须为正数 |
| `max_omega/omega_slew` | 旋转角速度上限及变化率上限；与驱动电机限速共同约束 |
| `rotation_priority` | 自旋工况下：1固定旋转、压缩平移；0平移/旋转超限时等比例缩放。高速自旋占用轮速余量时，设1会显著限制平移；相位补偿仍由工况标记独立控制 |
| `fixed_kp/schedule_kp/max_dv/dv_slew` | 主动补偿增益与权限，不能用大增益掩盖观测偏差 |
| `phase_lead_s/max_phase_lead` | 轮速响应延迟，仅用于自旋输出方向；新车默认 0 |
| `sample_max_us/sample_skew_us/dt_min/dt_max/recover_samples` | 实际采样周期、同步误差、时基异常拒绝、恢复所需新样本数 |
| `accel_consistency_window_s/accel_consistency_max_dv` | 默认0.25 s窗，`integral(a)-delta(v_wheel)`二维幅值≤0.04 m/s；按车轮/IMU时序与噪声标定，不可用增大阈值掩盖偏差 |
| `current_limit` | 与驱动器原始电流单位一致的饱和检测阈值；实际限流由硬件适配执行 |
| `ChassisMotionGetConfig/GetState/GetDirectionState/GetWheelCommand` | 读取最终配置、估计/控制状态、自旋方向提前、四驱动/转向目标 |
| `ChassisMotionGetObservationState/PopDiagnosticLog` | 读取观测门控、实际R、源诊断；日志出口同时弹出同一次入队的state、direction、observation |
| `ChassisMotionSetMode` | 选择 BASELINE、ESTIMATE_ONLY、SHADOW、ACTIVE_FIXED、ACTIVE_SCHEDULED |

若使用 `use_center_accel=0` 的平面兼容分支，只适用于已正确去重力且不随俯仰的安装。新车优先在 IMU 原始采样频率完成三维刚体补偿后使用中心分支，避免按底盘任务频率差分陀螺。

`MC_EXIT_GEOMETRY=9` 表示非法参数/奇异几何，`MC_EXIT_STEERING=10` 表示舵角不可用，`MC_EXIT_CLOCK=11` 表示时钟代次变化，`MC_EXIT_OBSERVATION=12` 表示轮速/加速度窗口冲突；原 0～8 原因码保持。日志状态仍为 444 字节，历史二进制帧仍为 456 字节。RTT 保留原六行并追加同seq的 OBS，frame14严格解析须七行完整；CLOCK为独立时间戳的低频摘要。舵角目标可用 `GetWheelCommand` 查看，未塞入历史状态布局。

移植时始终先调用 `ChassisMotionConfigDefault` 再覆盖字段，避免新增门控参数为0导致配置被拒绝。输入 `clock_generation` 应随时钟修复/失连续事件递增，即便修复后的当前dt正常，也能拒绝跨故障的滤波历史。源端在恢复期间置 `imu_recovering=1`（或维持 `accel_valid=0`）；仅数值有限并不能证明姿态去重力可信。其余新增姿态/重力字段用于诊断，未提供时可为0。

现车 INS 启动或时基/输入故障后，需要连续500 ms满足姿态已收敛、未拒绝重力观测、卡方比≤1、角速度<0.05 rad/s、加速度模长接近重力且水平运动加速度<0.10 m/s²，才释放运动观测；随后仍须完成内核一致性窗与KF恢复样本。该条件只用于恢复权限，不学习零偏、不重置公共YAW、不将零轮速当成地速真值。普通运动在恢复完成后不会因超过这些静置阈值而自动清零。

一致性窗口在固定N系比较加速度梯形积分与轮速速度变化。它支持不同源更新频率：IMU新样本积分，轮速新样本作为窗口端点；过期、时间异常或源失效则重新建窗。冲突时拒绝加速度融合，撤销主动补偿，并从实测轮速重建轮速诊断滤波；这不意味着确定轮速比IMU准确，也不能单凭冲突判定打滑。

现有 BSP 通过持续运行的 TIM14 HAL tick 核对 DWT，缺少的计数使能自动恢复，时间轴保持单调并记录修复代次。HAL tick分辨率为1 ms，修复并非恢复丢失期间的微秒真值；两种时钟同时随CPU暂停时也无法恢复墙钟时间。需要完整暂停时间时，应另接持续计时的硬件源。

## 8. 验证及使用边界

运行 `tests/run_chassis_motion_tests.ps1`，需要主机 GCC。覆盖三种独立物理轮型、逐轮标定、固定轮/舵轮限速、平行舵轮里程计、最短舵角与余弦补偿、底盘/云台 IMU 坐标、显式主动模式、超时/断连/计时回绕、CAN CRC 和一致性快照，以及现车 KF/杆臂/小陀螺延迟/PID 回归。

运行 `tests/build_chassis_variants.ps1` 可使用 PATH 中的 ARM GCC 构建三板型 × 三轮型共 9 份固件。默认输出目录为 `build/variants/<板型>_<轮型>/`，可通过 `-OutputRoot` 指定新目录，或通过 `-GccPath` 指定工具链的 bin 目录。以下命令使用 PATH 中的工具链单独构建一组：

```powershell
New-Item -ItemType Directory build/chassis_mecanum -Force | Out-Null
make -j4 BUILD_DIR=build/chassis_mecanum 'EXTRA_DEFS=-DCHASSIS_BOARD -DCHASSIS_DRIVE_MECANUM'
```

切换板型/轮型必须使用独立目录或完整重编译，Make 不会仅因参数字符串变化而自动重编译旧对象。9 组合通过表示编译/链接可行，其中三个云台板组合不运行底盘 KF；数学和接口测试不替代实际麦轮、舵轮硬件验收。

当前现工程的其他力矩、力跟踪、导纳控制仍基于原车全向轮分配器；麦轮/舵轮项目拒绝进入这些旧控制模式。若需要其他轮型力控，应另行实现对应力/电流分配与反馈，不能复用原全向轮矩阵。新轮型默认配置也不代表舵轮电机已经接线、注册和标定完成。

移植后先验证零补偿的前后左右、正反旋转、轮速与 IMU 导航系方向，再记录静止及启停/自旋数据。静止仍有显著加速度或假速度时保持影子模式，先处理安装、重力补偿、标定和时间基准；`estimate_valid=1` 只表示通过代码门槛，不能作为自动开启主动融合的充分条件。
